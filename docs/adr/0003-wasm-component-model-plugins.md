# 0003. WASM Component Model for plugins

Status: Accepted
Date:   2026-05-11

## Context

Plamenix is community-driven and Firebird-Foundation-funded. The
project must support third-party plugins from day one across both
editions (desktop and web). Plugins must:

- Be safe to load from untrusted sources.
- Ship as a single artifact across all desktop OSes.
- Survive plugin failures without crashing the host.
- Keep a stable contract for at least the 1.x lifetime.

## Decision

Plugins are written in **Rust**, compiled to the **`wasm32-wasip2`**
target, and loaded into the host by **`wasmtime`** using the **WASM
Component Model 1.0**. The host-plugin contract is described in
**WIT** files; Rust + TypeScript bindings are generated by
**`wit-bindgen`**.

Each plugin ships:

- A `.wasm` module (Rust half).
- An ESM bundle (React half, dynamically imported by the host).
- A `manifest.toml` declaring metadata, capabilities, and contribution
  points.

## Alternatives considered

- **Native dynamic libraries** (`.so` / `.dll` / `.dylib`) — fastest,
  but ABI-fragile per rustc release, requires per-OS+arch builds, no
  sandbox, plugin panic crashes the host. This is exactly DBeaver /
  OSGi's pain. Rejected.
- **Subprocess + JSON-RPC (LSP-style)** — strong isolation but heavy
  per-call IPC and high memory cost per plugin. Kept as an *escape
  hatch* (`manifest.runtime.requires_subprocess = true`) for plugins
  that genuinely need raw OS access.
- **Compile-time feature flags** — no third-party loading. Not a
  plugin system.
- **Embedded scripting (Lua, Rhai, Steel)** — user-script territory,
  not extension territory. Different problem.
- **Core WASM (not the Component Model)** — works but lacks the typed
  interface boundary the Component Model brings. Component Model 1.0
  is stable and gives us free type safety and language interop.

## Consequences

- One `.wasm` artifact runs on every desktop OS and arch.
- Plugin sandbox: plugins cannot access filesystem, network, or OS
  resources except through host-supplied, capability-gated calls.
- Plugin crashes are isolated traps; the host process keeps running.
- Cold startup is fast because WASM modules are instantiated lazily
  (only when first invoked); plugin manifests are scanned eagerly.
- Plugin authors must learn WIT / `wit-bindgen`. The SDK
  (`plamenix-plugin-sdk`) hides most of this with macros and
  examples.
- `wit-bindgen` is still pre-1.0 (`0.47.x`); pinned exact and watched
  for breaking changes.
- Performance: roughly 80–95 % of native for typical DB IDE workloads
  (Zed's published benchmarks; verified locally as plugins ship).
