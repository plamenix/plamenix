## docs-vs-reality

### [MAJOR] Canonical doc pledges "no process capability ever" while the code ships a runtime.subprocess escape hatch

`PLUGIN_ARCHITECTURE.md:216` · security-model-drift

**Problem.** The canonical architecture doc's strongest security promise — signed off twice — is contradicted by shipped code and by two sibling docs. §5 declares process capability 'Intentionally absent (no escape hatch ever)' and §19.4 records it as a resolved decision. Reality: capability.rs parses `runtime.subprocess`, manifest.rs routes `runtime.requires_subprocess = true` plugins to a native-binary activator (subprocess.rs) that spawns an arbitrary executable from the bundle — and the capability is self-granted by the plugin's own manifest. plugin-system.md (rewritten at I9.12 'to reflect shipped reality') and ADR 0003 both document the escape hatch as kept, so the project's own docs disagree about whether shell-out exists.

**Evidence.** PLUGIN_ARCHITECTURE.md:216-217: "**Intentionally absent (no escape hatch ever)**: `process` — no shell-out."; :726: "**\"No `process` capability ever\"** confirmed. First-party companion binaries handle anything that needs shell-out". Versus plamenix-core/crates/plamenix-plugin-host/src/subprocess.rs:3-5: "Plugins that opt out of the WASM sandbox set `runtime.requires_subprocess = true` in their manifest and ship a native executable at `entry_points.subprocess`. The host spawns the binary"; capability.rs:164: "[\"runtime\", \"subprocess\"] => Ok(Self::RuntimeSubprocess)"; plamenix/docs/plugin-system.md:53: "Subprocess + JSON-RPC | Kept as escape hatch for plugins that need raw OS access"; adr/0003:39-40: "Kept as an *escape hatch* (`manifest.runtime.requires_subprocess = true`)".

**Recommendation.** Pick one truth and propagate it. Either execute §17.7/§19.4 (delete RuntimeSubprocess, subprocess.rs, the manifest flag, and move keychain access to a host-mediated interface as the doc promises) or amend PLUGIN_ARCHITECTURE.md/§15.12/§19.4 (both copies) to admit the escape hatch exists, is desktop-only, and gets the stricter install warning capability-model.md describes. As it stands the security story a reviewer reads in the canonical doc is false.

**Verifier (high confidence).** Every evidence quote checks out verbatim. PLUGIN_ARCHITECTURE.md:216-217 declares process capability "Intentionally absent (no escape hatch ever)", line 576 repeats "no shell-out escape hatch", and line 726 records it as a signed-off resolved decision — yet the same doc's edition matrix at line 541 lists "Subprocess escape hatch ✓ (native binary) D-only" and §17.7 (line 705) still carries it as an open question, so the canonical doc contradicts itself as well as the code. The code fully ships the escape hatch: capability.rs:164 parses runtime.subprocess, manifest.rs:442-443 enforces the flag/capability pairing, activator.rs:73-74 routes to subprocess.rs, which spawns the plugin's own bundled binary (Command::new(bundle_dir.join(entry_points.subprocess))). plugin-system.md:53, ADR 0003:38-40, and capability-model.md:126-131 all document the hatch as kept. Aggravating detail found during verification: capability-model.md:130-131 promises a "stricter install-time warning" for runtime.subprocess, but plamenix-ui/src contains zero mentions of subprocess — that mitigation is unimplemented. One overstatement in the finding: "self-granted by the plugin's own manifest" holds only at the host-crate level; plamenix-desktop/src-tauri/src/plugins.rs persists user grants and PluginInstallDialog gates required permissions with accept-or-cancel consent, so the hatch is install-consent-gated and desktop-only, not silently self-authorizing. Severity lowered from critical to major: the drift is real and the canonical security story is false as written, but the shipped mechanism is deliberate (SDK helper, three sibling docs rewritten at I9.12 to reflect it), consent-gated, desktop-only, and not an exploitable bug or data-loss path; the plausible fix is doc reconciliation plus the promised stricter install warning, not architectural rework — significant pre-beta flaw, below the critical bar.

A plugin author reading the current contract will build a db-reader plugin that fails at instantiation with a raw linker error instead of the documented clean refusal.

**Verifier (high confidence).** Every factual claim verified by reading the code. (1) wit/plamenix.wit:376-415 declares 5 worlds while PLUGIN_ARCHITECTURE.md:591/700 say 4. (2) bindings.rs:21-26 is the only bindgen! in the workspace and targets plugin-minimal; activator.rs (lines 100-101, 173-174) links only register_host, whose surface (host_impl.rs:229-264) is log/host_version/edition — no db/fs/net/settings/command/clipboard/keyring import exists at runtime, so no higher-tier world can instantiate. **Verifier (high confidence).** Verified every cited quote on disk. ## plugin-host-rust

### [CRITICAL] Epoch preemption is inert in both shipping hosts: EpochTicker is never spawned, so a looping plugin activate() hangs the desktop boot forever

`plamenix-core/crates/plamenix-plugin-host/src/host.rs:58` · correctness

**Problem.** The engine enables epoch_interruption and the activator sets a 5s background deadline, but nothing in production ever bumps the epoch counter. `EpochTicker::spawn` has zero call sites outside the crate's own tests (grep across plamenix-desktop, plamenix-web, plamenix-cli: no matches for `EpochTicker`). With the counter frozen at 0, `set_epoch_deadline(500)` never fires, so `call_activate` on a malicious or buggy plugin that loops forever polls wasm indefinitely. In the desktop shell, `lib.rs` awaits `plugin_bootstrap(...).await` inside the splash sequence before `finish(&handle)` runs — a single hung plugin activate() means the main window never appears (splash hang, no timeout). In the web edition it permanently pins a tokio worker per hung activate call. The host.rs comment itself documents the failure mode as a known degradation, but neither host does the required wiring, and the 30s timeout that the subprocess path gets has no WASM equivalent.

**Evidence.** host.rs: "// counter every 10 ms; the activator + dispatchers call\n// `Store::set_epoch_deadline` per call to preempt runaway\n// plugins. Without the ticker, no preemption happens —\n// hosts that omit the ticker get an effectively-unbounded\n// deadline". plamenix-desktop/src-tauri/src/lib.rs:104: "plugin_bootstrap(&host, &host_version, &plugins_root, &grants_store).await" runs before "finish(&handle);" — the splash/main-window handoff blocks on plugin activation. Grep for EpochTicker in plamenix-desktop + plamenix-web returned nothing.

**Recommendation.** Spawn one `EpochTicker` per process at each host's boot path (Tauri setup closure, NAPI module init next to the `OnceLock<PluginHost>`) and keep the handle alive for the engine's lifetime. Additionally wrap the desktop bootstrap's per-plugin activate in `tokio::time::timeout` as belt-and-braces so boot can never hang on one bundle.

### [MAJOR] Subprocess activation timeout orphans the child process: Command lacks kill_on_drop, so the native binary keeps running after the host reports failure

### [MAJOR] Signature verification has no trust root — any attacker-generated key verifies as "Signature verified"

`plamenix-core/crates/plamenix-plugin-host/src/signing.rs:280` · signing-trust

**Problem.** `verify_archive` reads `public_key` out of the archive's own `signature.json` and verifies the archive against it. ### [MAJOR] `runtime.subprocess` escape hatch ships, and the binary path it executes is manifest-controlled and unconfined

`plamenix-core/crates/plamenix-plugin-host/src/subprocess.rs:79` · code-execution

**Problem.** Two problems stacked. (1) The signed-off decision is "No `process` capability ever" — the host nevertheless implements `Permission::RuntimeSubprocess`, a `[runtime] requires_subprocess` flag, and a `tokio::process::Command` spawn, all publicly re-exported (`pub use subprocess::activate_subprocess`). **Evidence.** subprocess.rs:79 `let binary: PathBuf = staged.bundle_dir.join(rel);` then line 93 `let spawn = Command::new(&binary)`; subprocess.rs:148-154 `fn require_subprocess_capability(manifest: &Manifest) { if manifest.permissions.grants(&Permission::RuntimeSubprocess) }` — manifest-self-attested. **Recommendation.** Delete `subprocess.rs`, `Permission::RuntimeSubprocess`, `RuntimeFlags::requires_subprocess`, and `EntryPoints::subprocess` before beta — §17.7 of the design already recommends removal. ### [MAJOR] Firebird attachments are never reaped — sessions live forever unless the browser politely calls /api/close

`plamenix-web/packages/server/src/sessions/store.ts:1` · resource-leak

**Problem.** SessionStore records only `{id, createdAt}` and exposes register/has/drop/size — there is no idle timeout, no sweeper timer, no cap on concurrent sessions, and no association between a session and the browser that created it. **Evidence.** sessions/store.ts:1-5 `// In-memory session store for M1. … so we can expire stale sessions or report active count from the server side.` and :12-32 — the class body is exactly `sessions = new Map()`, `register`, `has`, `drop`, `size`; no timer, no ttl field. execute.ts:29-31 is the only gate: `if (!sessionStore.has(parsed.data.sessionId)) { return reply.code(404).send({ error: 'unknown_session' }); }`.

**Verifier (high confidence).** Confirmed by direct reading. store.ts:12-32 is exactly the quoted skeleton — {id, createdAt} entries with register/has/drop/size; createdAt is never read; no timer, TTL, or cap, despite the :1-5 comment promising stale-session expiry. sessionStore.drop is called exactly once in the whole server, at execute.ts:96 inside POST /api/close. buildApp (app.ts) registers no sweeper or onClose cleanup, and connect.ts:48-49 registers sessions unconditionally with no MAX_SESSIONS check. ### [MAJOR] Export is not actually streamed and has no row cap — one export materialises the whole result set four times in a process shared by every user

`plamenix-web/packages/server/src/routes/export.ts:37` · performance

**Problem.** The route's doc comment promises progressive delivery, but `await fbclient.exportQuery(...)` runs to completion first: export_query in the NAPI crate executes each SELECT, collects every row into a Vec, builds the entire deliverable as one Rust String, hands it to V8 as a JS string, and the route then copies it again into a Buffer before chunking. So the payload exists ~4x concurrently (driver rows + Rust String + V8 string + Buffer) and time-to-first-byte is the full export duration. Critically, export_query never applies the ROW_LIMIT that execute_batch applies — `SELECT * FROM <table>` for a table-scope export is unbounded — so exporting a large table is an OOM of the whole multi-user server process, taking every other user's sessions with it. The client discards the chunking anyway (`await response.blob()`), so the 64 KiB loop buys nothing today.

**Evidence.** export.ts:37-42 `Server-streamed export. … writes the result to the HTTP response in 64 KiB chunks via the raw stream so the browser sees the bytes arrive progressively rather than waiting for the full body.` then :55 `const output = await fbclient.exportQuery(` and :82 `const buf = Buffer.from(output, 'utf8');`. fbclient-node/src/lib.rs:39 `const ROW_LIMIT: u32 = 10_000;` is used only in execute_batch (:258-269); export_query :348 builds `let sql = format!("SELECT * FROM {ident}");` and :358-364 pushes every row into `payloads` with no cap. packages/client/src/App.tsx:897 `const blob = await response.blob();`.

**Recommendation.** Either make export genuinely incremental — have the NAPI side expose a cursor/callback that yields formatted chunks (ThreadsafeFunction or an async iterator) so the route can pipe them without full materialisation — or, if that is post-beta, cap it honestly: apply an EXPORT_ROW_LIMIT per statement in export_query, return the truncation flag to the client, and delete the misleading 'progressively' comment plus the 64 KiB loop since nothing consumes it.

**Verifier (high confidence).** Confirmed by direct reading. export.ts:37-42 promises progressive delivery but line 55 awaits fbclient.exportQuery to completion and line 82 copies the whole string into a Buffer before the 64 KiB loop; the client (App.tsx:898, finding said 897) does `await response.blob()`, discarding any chunking benefit. Refutation attempts failed: the repo CLAUDE.md's "no Buffer/stream trickery in the first cut" rule explains the full-string NAPI return but not the false 'progressively' comment nor the missing cap that execute_batch deliberately applies; export is not on the known-issues exclusion list; the OOM scenario is reachable with any sufficiently large table. ### [CRITICAL] Shipped `runtime.subprocess` capability + native-binary activator contradict the canonical "No process capability ever" decision

`plamenix-core/crates/plamenix-plugin-host/src/capability.rs:164` · design-drift-security

**Problem.** PLUGIN_ARCHITECTURE.md (workspace-canonical) refuses a process capability three times — anti-pattern 12, open question 7 ("Recommend remove entirely"), and Resolved decisions §19.4 — yet the implementation ships exactly that escape hatch: `Permission::RuntimeSubprocess` is part of the capability grammar, and `subprocess.rs` spawns arbitrary native executables from plugin bundles via tokio `Command` when a manifest sets `runtime.requires_subprocess`. `plamenix/docs/capability-model.md` documents it as legitimate grammar ("runtime.subprocess  # opt out of WASM sandbox"), so the two design docs now contradict each other and the code follows the non-canonical one. ### [MAJOR] Large-result flow is a single monolithic payload on both editions: 10k rows x all statements in one Tauri invoke / one NAPI double-marshal, no chunking

**Problem.** Desktop: `db_execute` returns `Result<Vec<StatementOutcome>, String>` — the entire batch (each SELECT up to ROW_LIMIT=10_000 rows) crosses the Tauri IPC bridge as one JSON response and is parsed on the WebView main thread in one go. **Evidence.** db.rs:18-21: "Hard cap on rows surfaced to the UI per SELECT statement.
