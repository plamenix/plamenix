# NAPI bindings for rsfbclient

The web edition (`plamenix-web`) runs on Node.js / Fastify. Rather than
shipping a parallel Firebird driver implementation in Node, Plamenix
exposes `rsfbclient` to Node via NAPI bindings. One driver, one quirks
list, one truth.

## Binding package

- npm name: **`@plamenix/fbclient-node`**
- Source: lives inside `plamenix-web/` (alongside the Fastify code that
  depends on it) or as a separate `plamenix-fbclient-node/` repo if it
  grows.
- Built with [`napi-rs`](https://napi.rs/) — the modern Rust → Node
  binding toolchain. Pre-built native modules per platform / arch.

## Why NAPI, not node-firebird

| Option | Verdict |
|--------|---------|
| **NAPI binding to rsfbclient** | **Chosen.** Same driver, same behaviour as desktop. One truth across editions. |
| Keep `node-firebird` from MVP | Rejected. Driver quirks (MON$, BLOB callback, BOOLEAN params, ARRAY descriptors) we are explicitly leaving behind. Maintained inconsistently with rsfbclient. |
| HTTP-only proxy (web → Rust binary subprocess) | Rejected. Heavyweight per-request IPC; loses connection pooling; would require running a Rust sidecar process under the Fastify host. |
| Alternative Node FB driver | None mature enough at audit time. |

See [adr/0014-napi-rsfbclient-bindings.md](./adr/0014-napi-rsfbclient-bindings.md).

## Surface

The binding exposes the same set of operations that the Tauri
edition exposes via `#[tauri::command]`. Internally it converts JS
inputs into the `DbDriver` trait surface from `plamenix-core` and
returns serialised results.

```ts
// @plamenix/fbclient-node — illustrative surface
export class FbConnection {
  constructor(config: ConnectionConfig);
  attach(): Promise<SessionId>;
  detach(): Promise<void>;
  query<T = unknown>(sql: string, params?: unknown[]): Promise<QueryResult<T>>;
  // ...
}

export function loadNativeFbclient(path: string): void;
```

Types are generated by `napi-rs` from the Rust side; we re-export them
into `@plamenix/types` for use by `@plamenix/ui`.

## Async model

`rsfbclient` is synchronous. The binding wraps every call in a Tokio
blocking worker thread on the Rust side and returns a real JavaScript
`Promise` to Node. Fastify handlers `await` the call normally.

## Connection lifecycle (web)

- A Fastify session corresponds to a logged-in user's interaction with
  Plamenix.
- Each session opens its own `FbConnection` via the binding.
- Per-tab semantics inside a session mirror desktop: each tab owns its
  own attachment.
- Idle sessions time out (configurable; default 30 minutes) and their
  attachments are dropped.

## Bundling

Per-platform native modules ship inside `@plamenix/fbclient-node`:

```
@plamenix/fbclient-node/
├── package.json
├── index.js
├── index.d.ts
└── native/
    ├── plamenix-fbclient.linux-x64-gnu.node
    ├── plamenix-fbclient.linux-arm64-gnu.node
    ├── plamenix-fbclient.darwin-x64.node
    ├── plamenix-fbclient.darwin-arm64.node
    └── plamenix-fbclient.win32-x64-msvc.node
```

CI builds these on each platform; npm publishes them as platform-tagged
optional dependencies, following `napi-rs` convention.

The native fbclient binaries themselves (`libfbclient.so` /
`fbclient.dll` / `libfbclient.dylib`) are still loaded at runtime via
`with_dyn_load(<path>)`; the binding does not bundle Firebird's
fbclient.

## Versioning

`@plamenix/fbclient-node` follows the Plamenix lockstep version line
(`1.0.0-beta`).

The Rust source crate inside `plamenix-web/` (or its dedicated repo)
sets `version.workspace = true` and inherits.

## Open work

- Decide whether the binding lives **inside** `plamenix-web/` (simpler
  ownership) or **as its own repo** `plamenix-fbclient-node` (cleaner
  reuse, but more polyrepo coordination). Default for now: inside
  `plamenix-web/`; split later if it earns its own repo.
